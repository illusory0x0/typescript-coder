# Consumption ledger

Canonical before/after view for the efficiency series: the pre-series baseline
and each measured result side by side, with a source result file per row. Metric
values are **USD per success** — the total USD cost of a row's runs divided by
the number of passing runs, the same definition as `aggregates[].costPerSuccess`
in the result JSON — on the tc side unless a note says otherwise. Every
historical row falls in an off-peak window and is converted at the off-peak
rate; new rows price by their own window (a calculator estimate — run timing is
not a constraint; see [Method](#method)). Success counts are shown as `ok/runs`;
the dated reports keep the token columns, and `benchmark/README.md` documents the
pricing rule.

## Row format

| Date | Change set | json-parser | sexp-parser | minilisp | Overall | Source | Notes |
| ---- | ---------- | ----------- | ----------- | -------- | ------- | ------ | ----- |

- `Date`: measurement date (the result run's date).
- `Change set`: series issue refs and/or a short description of what changed
  relative to the previous row; the baseline is `baseline (pre-series, plan v4)`.
- `json-parser` / `sexp-parser` / `minilisp`: tc-side USD per success with the
  success count, e.g. `$0.00104 (3/3)`, from `aggregates.byTaskSide[].costPerSuccess`.
- `Overall`: tc-side totals across all three tasks, e.g. `$0.00438 (8/9)`, from
  `aggregates.bySide[].costPerSuccess`.
- `Source`: path of the result JSON the row was copied from (report path when
  useful). Paths are relative to the repository root.
- `Notes`: caveats, cross-side reference values, or anything the numbers do not
  show on their own. Notes may keep token-era figures from the original reports;
  those are labeled where they carry a claim.

## How to add a row

Run the tc-side matrix (`bun run benchmark/run.ts --all --side tc --reps 3`),
copy `costPerSuccess` from `aggregates.byTaskSide` (per task) and
`aggregates.bySide` (overall) in the result JSON, cite the result JSON path, and
append the row below the existing rows. Values are USD per success rounded to
five decimals with the success count, e.g. `$0.00438 (8/9)`. Rows are appended in
series order; the final row is added during the #46 close-out.

## Method

USD values use the official DeepSeek V4.1-Flash prices (fetched 2026-10-19 from
<https://api-docs.deepseek.com/quick_start/pricing>; USD per 1M tokens): cache-hit
input $0.006 peak / $0.003 off-peak; cache-miss input $0.30 / $0.15; output
$1.20 / $0.60. Peak hours are Mon-Fri 01:00-04:00 and 06:00-10:00 UTC excluding
Chinese public holidays; every other hour is off-peak.

Historical rows predate the recorded `startedAt`/`finishedAt` fields and all ran
inside off-peak windows (weekends UTC), so they are converted at the off-peak
rate. New rows are priced from the run's window and its rate class (`peak`,
`off-peak`, or `mixed`; a run straddling a boundary splits by elapsed-time share
— a uniform-spend approximation). These USD values are a calculator estimate,
not provider billing: the endpoint is a relay and does not bill on DeepSeek's
schedule, so run timing is not a constraint and runs are not scheduled off-peak.

Bucket normalization: tc `input` includes cache hits (miss = input - cacheRead);
oc `input` excludes them (miss = input, hit = cacheRead); output is priced
together with reasoning; `cacheWrite` is priced at the cache-miss rate. The
`opencode session export` payload's own `cost` matches the computed value within
1e-9 relative on every recorded oc baseline run. Implementation:
`src/benchmark-pricing.ts`.

## Held-out task rule (#67)

`csv-parser` is the held-out fixture. It is never the target of prompt or loop
iteration, and a held-out result is never a change-set's evidence of *prompt
fit* — it gates only "generalizes beyond the tuned fixtures" claims. Every
series matrix includes it (`--all`), so its column is recorded like the others,
but a change-set must not cite a held-out movement as a gain on the three tuned
fixtures. The first held-out baseline row is listed among the tc rows above.
